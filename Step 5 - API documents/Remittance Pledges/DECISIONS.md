### Decisions taken this pass (unattended run: approval gates defaulted and reported, fact gates never defaulted)

1. **The `receiptsThrough` deprecated alias is dropped from the V2 contract.** The V1 spec kept it for existing callers; no production caller of the modern endpoint exists yet in the re-platform, so the alias is dead weight in a fresh contract. DEFAULTED - reinstate in one line if the owner disagrees.
2. **API 1 gains a response envelope** (`rangeStart`/`rangeEnd` echo + `activities[]`) instead of the V1 bare array, so the resolved range is visible and state contracts have a shape. DEFAULTED.
3. **`pageSize` maximum set to 100** on API 2 (default 8 per the build's `REMF_PAGE_SIZE`). The maximum is invented to close the unbounded-pageSize hole; the number is arbitrary within reason. DEFAULTED.
4. **`rangeStart > rangeEnd` rejected with `INVALID_RANGE`** rather than swapped or ignored. DEFAULTED.
5. **Cache posture LIVE per request** for APIs 1-3 (the legacy file cache `RMWidgetRecord` is not carried over; its company-change isolation requirement is). DEFAULTED.
6. **Export included as API 4** (server-side file over the full filtered set; the build's Export is a Rule 11 stub signalling intent). Format/mechanics left open in Still needs sign-off. DEFAULTED inclusion.
7. **Pledge-list sort fixed server-side** (`shortfall DESC, pledgeId ASC`), no `sortBy`/`sortDir` exposed, matching the build's drill which has no sort controls; the loss (no column re-sort) is stated in the spec. DEFAULTED.
8. **Activity-level term fields defined as MIN(BeginDate)/MAX(EndDate)** over in-scope pledges, flagged as a working definition with the mixed-term display rule left open (Still needs sign-off row 7). DEFAULTED definition, open item kept.
9. **API 2 returns its own full-set `summary` block** rather than the client reusing the API 1 row, so the drill reconciles to figures computed at open time; the contract requires the two to agree for the same range. Derived from the consistency counter-pressure in the frameworks.
10. **Activity `expected` defined as `SUM(per-pledge expectedByNow)`**, not the activity total paced over a single term. This is the only definition consistent with per-pledge terms and with the build's cents-exact drill reconciliation; the V1 formula (activity total over one term) silently assumed a single shared term.
11. **Donor names are in the contract** (`CorePerson.DisplayNameLastFirst` on APIs 2-4). The V1 spec's "no personal or payer data" boundary predates the pledge-drill design; the locked Step 4 design shows person names in the drill, so the contract follows the design and flags the permission question instead.

### History harvested from the V1 spec (kept here so the V2 body stays present-tense)

- The V1 spec was reopened to Draft on 2026-08-24 when the widget was rebuilt (v3.0-v3.2) as the EXCEPTION side of the pledge pair (W17 owns goal progress, direct instruction 2026-08-24).
- **Driver: SME correction on the date control.** Edward Eoff, 2026-08-10: the legacy "Date Receipts Through" is really 1 January of that year through the selected date, verified live; the window does two jobs (pledge scope + which receipts count); his preferred enhancement was a user-controlled two-ended range; and the control must never be labelled "fiscal".
- **The one trap, learned mid-build 2026-08-24:** the frontend window-bounded `paid` and every pledge read as catastrophically behind (a windowed numerator against a cumulative denominator, e.g. a false $37,085 shortfall vs $13,090 on the year window). Hence the spec's standing rule: pacing is cumulative; `rangeStart` touches only `windowPaid` and pledge scope.
- **Aggregate shortfall rule** (sum per row, never net) was added 2026-08-24 with the exception repositioning; on the then-seeded data the summed figure was $8,268 vs a smaller netted one.
- The **pledge-in-scope overlap rule** replaced the live single-instant filter on 2026-08-24, partly resolving the long-standing ended-but-unpaid drop-off item (Pending Questions item 12 documents the live filter: `BeginDate <= date <= EndDate`, no `Active` check).
- **API 3 (payment schedule)** was added by the v3.1 build's third drill level (2026-08-24); its oldest-first allocation is carried into V2 unchanged. The v3.4 build (2026-08-30) cut the page size 20 to 8 and fixed a `.map(fn)` arity bug that had made schedules impossible to expand in the bars popup since v2.3.
- **The V1 "API 2: Activity Payment History" (receipts list popup) is NOT in the V2 contract.** The receipts popup has been a preserved rollback path (`REMF_USE_POPUP`, default false) since 2026-08-08 and is unreachable in the locked design; v3.5 (2026-08-30) replaced the popup content with the top-5-most-behind list served by the pledge-list API. The receipts-list field source map (this folder, 2026-08-08) remains the provenance reference if that view ever returns.
