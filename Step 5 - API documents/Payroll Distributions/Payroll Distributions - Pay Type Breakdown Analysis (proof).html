Payroll Distributions — Pay Type Breakdown

Technical Analysis  ·  Shelby Financials  ·  July 2026

Bottom line up front: Yes — a full breakdown of distribution amounts by pay type (Regular, Overtime, Sick, etc.) down to individual employee checks is supported by the underlying database. Every field needed already exists in a single table. The current widget only surfaces the top-level totals. A drill-down endpoint can be built without any schema changes.

1. How the Data Hierarchy Works

The question is essentially: given a distribution like "Administration Staff" with a total of $4,530.63, can we see who received that money and in what form? The answer is yes, and here is how each level maps to the database:

LevelWhat it representsDatabase table(s)
1 — Total Combined payroll distribution amount across all distributions for the selected date range PR_HistoryCompensation — SUM of all Amount
2 — Per Distribution Amount allocated to a named distribution category (e.g. AA Aid, Administration Staff) PR_HistoryCompensation → PR_CompensationDistribution.Name
3 — Per Employee / Per Check Individual payroll check for one employee — who received it, when, total hours, total amount PR_History (the check) + PR_Employee (the person)
4 — Pay Type Breakdown How each check breaks down: Regular hrs at $X/hr, Overtime hrs at $Y/hr, Sick hrs, Holiday, etc. PR_HistoryCompensation — SubType + Hours + Rate + Amount

The key insight is that levels 2 and 4 both come from the same table — PR_HistoryCompensation. Each row in that table is one compensation line on one paycheck. It already stores the distribution it belongs to AND the pay type, hours, and rate. The current widget only reads the Amount and CompensationDistributionID columns — it ignores the rest.

4. Pay Type Codes — SubType Field

This is the field that answers "what kind of pay was this?". These are the same options visible in the payroll check entry screen (Regular, Overtime, Double Time, etc.):

CodeShort nameFull nameNotes
1RegRegularStandard hours/pay. Salary workers log their standard hours here; hourly workers log actual hours worked.
2OTOverTimeHours beyond the normal working week — typically paid at 1.5× the regular rate.
3DTDoubleTimeHours at 2× rate — applicable in certain circumstances depending on employment terms.
4HolHolidayHours or lump amounts paid for recognised holidays.
5OtherOtherCatch-all for additional hours-based pay that doesn't fit the standard types.
6VacVacationName is configurable per organisation — some use different labels (e.g. "Annual Leave").
7SickSickName is configurable per organisation.
8PersPersonalName is configurable per organisation.
9MiscMisc.Name is configurable per organisation.
10Other PayOther PayTypically non-hours-based supplementary payments.
Hourly vs. Salaried: The system distinguishes between the two via a Classification field on the employee's compensation record. For hourly workers, Amount = Hours × Rate and both fields are directly meaningful. For salaried workers, Amount is the period salary, and Rate holds the same value — Hours may still carry a standard hours figure for reference (as shown in the legacy payroll entry screen at 8.00 hrs for a salaried employee).

7. Additional Findings Worth Knowing

  • Pay type names are organisation-configurable. SubTypes 6–9 (Vacation, Sick, Personal, Misc) do not have fixed names — each organisation sets its own labels in the PR_Company settings. So "Vacation" might be labelled "Annual Leave" or "PTO" depending on the client. The API would need to resolve these names from the company configuration at query time.
  • Non-cash compensations are separate. Benefit items like health insurance contributions, car allowances, and similar non-cash pay flow through a different table (PR_HistoryNonCash). These are not included in the distribution totals and would not appear in the breakdown — the widget is strictly about cash compensation.
  • Voided checks are already excluded. The current widget filters out voided checks (VoidJournalID IS NULL). Any drill-down would maintain this same filter, so reversed/voided pay does not appear.
  • Manual checks (CheckType = 2) are excluded. The current widget also excludes manual check type 2. This is intentional and should be maintained in any drill-down to keep the numbers consistent with what the top-level widget shows.
  • Project coding is available. For organisations that code payroll to projects, each compensation line has an optional ProjectID. This means the drill-down could eventually support a project-level breakdown as well if that becomes a requirement.
  • Workers' Comp classification is per line. Each compensation row has a WorkersCompID which identifies the workers' comp insurance category for that specific type of pay. Not relevant for the immediate request but available if the need arises.
On the "how much per hour" question specifically: For hourly employees, the per-hour rate is directly available in the Rate column on each PR_HistoryCompensation row. For salaried employees, the Rate stores the per-period salary amount — not an hourly rate — because salaried pay is a fixed amount regardless of hours. To derive an implied hourly rate for a salaried employee, you would divide their period salary by their standard hours, but this is a calculation rather than a stored value.

8. What Would Need to Be Built

No database changes are needed — all the data exists. The work is entirely on the API and UI side:

ComponentChange neededComplexity
Modern API — entity Extend PRHistoryCompensation to map Hours, Rate, SubType, and join to PR_Employee via PR_History for employee name Low
Modern API — DTOs New PayrollDistributionBreakdownDto with nested employee → pay type structure Low
Modern API — service method New GetPayrollDistributionBreakdownAsync(distributionName, startDate, endDate) — queries PR_HistoryCompensation with SubType, Hours, Rate, and joins to employee for name Medium
Modern API — controller New endpoint: GET /api/dashboard/payroll-distributions/breakdown Low
UI — drill-down view Clickable distribution rows that open a detail panel showing the per-employee, per-pay-type breakdown table Medium

9. Summary

QuestionAnswer
Is the breakdown data in the database?Yes — completely. Hours, Rate, SubType, and classification are all stored in PR_HistoryCompensation.
Can the system tell if a worker is hourly or salaried?Yes — Classification field on the employee compensation record.
Can hours per pay type per employee per check be retrieved?Yes — Hours + SubType + HistoryID give this exactly.
Can the hourly rate be retrieved?Yes for hourly workers — the Rate column stores it. For salaried, Rate is the period salary amount, not an hourly figure.
Does the current widget expose this?No — it only reads Amount and CompensationDistributionID.
Can it be built?Yes — no schema changes needed. New API endpoint + UI drill-down, medium overall effort.
