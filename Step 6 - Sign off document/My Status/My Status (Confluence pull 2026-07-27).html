Part A. What exists today

1. What it is

A personalised status panel. Each row is a saved query - a question asked of the system ("how many unposted journal entries?", "purchasing requests needing my approval") - showing a live count. The user chooses which queries to show, so the widget is different for every person. It surfaces where work is waiting and links to it. It is best understood as a personalised "what has a count I should look at" router - distinct from a task-shortcut launcher.

2. Where the data comes from

Each row runs its own query against its own area of the system; only queries the user has rights to are offered. The user's chosen set is saved as a preference (UserPreferences.MyStatus) and remembered across sessions. Per-query source tables are not yet documented (prior doc, to confirm).

3b. The query catalogue (what can be tracked)

21 queries are available, spanning four areas - which is itself a design signal (the list needs grouping):

  • GL / posting: My Unposted Journal Entries; Unposted Journal Entries; My Unposted Bank / Credit Card / AP Transactions; My Unposted Payroll Manual Checks; GL Accounts Added in Last 30 Days; Check Register Summary; Check Register Detail.

  • Accounts Payable: Unpaid Accounts Payable by Due Date; AP Recurring Dollars by Due Date.

  • Purchasing: Purchasing Requests Needing My Approval; ...Needing My Approval Next.

  • Payroll / HR: Employees Needing Review Now / Within Next Month; Active Employee Time Clock Info; Employee Overtime Hours Last Payroll; Scheduled Time Off; Employee Birthdays This Month / Next Month / Next Week.

The names are system phrasing ("AP Recurring Dollars by Due Date") rather than plain language, and mix urgent work (approvals, unposted entries, overdue AP) with low-urgency notices (birthdays) at the same visual weight.

4. Caveats

Accessibility looks better than the chart widgets (values are table text), but the row icons and keyboard operability still need a check.

Part B. Users and market

5. Personas

My Status is the most cross-role widget, because its query set spans GL, AP, Purchasing and Payroll/HR. The bookkeeper/administrator (P1) is the likely primary user (daily scan of unposted entries, approvals, AP due). Approvers (purchasing) and supervisors (reviews, time off, overtime) use their slices. Oversight personas use it least. Note: this is an inferred fit from the widget's function; the SME did not speak to My Status specifically (see 8b).

7. Context scenarios

A. Daily scan - bookkeeper opens the dashboard and checks which counts are non-zero. B. Approver opens the records behind a purchasing-approval count. C. Month-end - "any unposted entries anywhere?". D. Supervisor checks reviews due / time-off / overtime. E. New user opens it and sees a blank widget - doesn't realise it must be configured (the adoption killer).

8. Competitor and analog benchmark

Desktop research The relevant analog is the status / "items needing attention" pattern (Xero dashboard watchlist and account counts, QuickBooks review counts, OS notification centres). Best practice for actionable dashboards: only actionable + frequent items belong up front; give each item context and a next step, not just a number; use severity/urgency cues; pre-configure sensible default states rather than starting empty; and let users customise. Sources: Improvado, Brand.dev, DataCamp.

8b. What the SME did and did not say. SME Ben Lane (Marvin) did not reference My Status. His "used every day / highly valuable" comments were about an existing "My Tasks" widget - a functional task-shortcut list whose limitation is that it just says "enter transactions" without identifying the module - and he wanted it improved with more user control and a consolidated view of standard and saved tasks. That maps to the task-shortcut concept (closest existing widget: Main Content Tasks), not to My Status. Whether "My Tasks"/"My Reports" are literally Main Content Tasks or separate legacy Shelby features is to confirm. My Status's value here is therefore an inference from its function, not a direct SME endorsement.

Part C. Designer brief

9. Target composition (what the widget should be built from)

The concrete make-up, so it can be built and demoed consistently. A floor, not a straitjacket. Triage: P current production (keep what works, delete nothing used), C competitor, SME Ben Lane, DR desktop/best practice, O Oisin's demo.

Controls (header):

  • Configure (rename from "Select", which is the live control label verified 23 Jul 2026) - the dual-list picker, kept, but with the available list grouped by area (GL, AP, Purchasing, Payroll/HR), searchable, and using plain-language labels. [P + DR]

  • Group-by / sort toggle (by area, or by urgency). [DR prioritise]

  • Refresh with a "data as of" timestamp. [P pattern]

Content (the list):

  • A grouped, prioritised list. Each row: plain-language label + count + light context where it exists (e.g. total $ or oldest due date for AP; "3 overdue") + an affordance icon showing what a click does. The live columns are Query | # Records (verified 23 Jul 2026). [P rows; DR context + severity]

  • Sensible default set for a new user by role (e.g. unposted entries, approvals pending, AP due) instead of the live empty state "No records to display" (verified 23 Jul 2026). [DR default states]

  • Urgency treatment: visually distinguish action-now items (approvals, unposted, overdue AP) from informational ones (birthdays); highlight overdue/critical. [DR severity levels]

  • Zero-count rows dimmed or hidden (user option), not full-weight clutter. [P today shows them non-clickable]

Interaction & rules:

  • Make the two row behaviours predictable: prefer opening an in-widget focus overlay (records + Export + a "go to page" link) as the default, and clearly mark rows that leave the dashboard with an external-link icon. Never leave the user guessing which will happen. [P inconsistent today]

  • Counts and labels as text (already true - keep it); name every icon; fully keyboard operable. [accessibility]

  • Respect rights: only show permitted queries (already true). [P]

11. Significant design decisions

11.1 Default, don't start empty. The single biggest lever for adoption is a sensible role-based starter set, since a blank widget is invisible value. 11.2 Add priority/urgency and context - a count alone is not actionable; overdue AP and pending approvals should outrank birthdays, and money/oldest-date context helps. 11.3 Group by area - the 21 queries span GL/AP/Purchasing/Payroll-HR; grouping makes a long personalised list scannable. 11.4 One predictable click model - resolve the open-here-vs-navigate-away inconsistency; prefer in-widget focus, mark links that leave. 11.5 Plain-language labels - relabel system query names. 11.6 Clarify the relationship to the task-shortcut widget - My Status (counts) and the SME's "My Tasks" / Main Content Tasks (functional shortcuts) are complementary; decide deliberately whether they stay separate or converge, rather than letting them blur.
