Part A. What exists today

1. What it is

Gives supervisors a view of all scheduled time-off requests across their departments (by department, then employee, then day), showing pending vs approved, and lets them approve directly from the widget without navigating elsewhere (an explicit reject/deny action is not present today - see Part C). It is the dashboard's PTO approval queue.

SME Along with Purchasing Management, this is one of only two widgets where the user can take action; it is the concrete model for the SME's repeated ask to make widgets actionable (Marvin).

2. Where the data comes from

The Payroll module - time-off records for departments the logged-in user is authorised to approve; each supervisor sees only their own departments. Year and view filters saved per user. Tables: PREmployeeTimeOffApprovals (which departments a supervisor approves), PayrollScheduledTimeOffFilters (saved filter prefs), and the individual time-off records (exact table to confirm). Part B. Users and market

5. Personas

Approver-centric. The supervisor / department head is the primary user - clearing their team's time-off requests. A payroll administrator has oversight. The widget is permission-scoped so each supervisor sees only their own departments. Employees are indirect beneficiaries (their requests get actioned).

7. Context scenarios

A. Supervisor clears the pending queue for the week. B. Bulk-approve an employee's whole request in one click. C. Check coverage before approving overlapping requests (hard today - no calendar). D. Review approved time-off for the year. E. Reject a request that clashes with a deadline (needs a clear reject path).

8. Competitor and analog benchmark

Desktop research PTO/leave-approval tools (BambooHR, Gusto, Vacation Tracker, Teamup, Day Off) center on informed approvals: the biggest failure is approving one request at a time without seeing coverage conflicts, so a shared team calendar of pending + approved together is the key practice. They also surface a pending count/queue (avoid the "silent pending request"), keep an audit trail (who approved, when, leave type), and support bulk actions, blackout dates and balances. Sources: Teamup (calendar visibility), Cflow (SLA, audit), Vacation Tracker (shared calendar), Day Off (coverage before approving).

Part C. Designer brief

9. Target composition (what the widget should be built from)

The concrete make-up, so it can be built and demoed consistently. A floor, not a straitjacket. Triage: P current production (keep what works, delete nothing used), C competitor, SME Ben Lane, DR desktop/best practice, O Oisin's demo. This widget is the reference pattern for in-widget action - preserve that and build the rest around it.

Controls (header):

  • Year and View (Show All / Pending / Approved), saved per user - default the View to Show Pending (the actionable set). Refresh with a "data as of" timestamp. [P; DR]

Views:

  • Glance (KPI): number of requests awaiting my approval (+ how many employees affected). [DR pending-queue]

  • Approval queue (keep): the Department -> Employee -> Day structure (expand chevron per employee) with hours-by-type and the audit stamp ("Approved by: name, date"). [P]

  • Coverage / calendar view: a month calendar grid already exists in production (verified live 23 Jul 2026); enhance it to show who is off when, pending + approved together, to spot overlaps before approving. [P; DR top practice]

Interaction & rules:

  • Preserve inline approve - the per-employee Approved checkbox (verified live 23 Jul 2026) is the exemplar the other widgets should follow. Add bulk approve (absent today). [P; SME]

  • Make reject explicit - a clear approve / reject / pending state (an explicit reject/deny is absent today), rather than a single checkbox where unchecked = reversed; keep the audit trail and add confirmation/undo. [DR audit; clarity]

  • Keep it permission-scoped (own departments only). [P]

  • Accessibility: labelled checkboxes, keyboard operation, an accessible expandable tree. [Pathway AA]

Bulk approve should confirm; all actions reversible with an audit trail.

11. Significant design decisions

11.1 Preserve inline approve/reject - the one widget that already does what the SME wants everywhere; treat it as the reference pattern for My Status / AP / Purchasing. 11.2 Add a pending KPI and default to Show Pending - surface the actionable count so requests don't sit silently. 11.3 Add a coverage/calendar view - the top PTO best practice is seeing overlaps before approving; a status list alone hides conflicts. 11.4 Make reject explicit - approve / reject / pending as distinct states with an audit trail, not a single checkbox. 11.5 Keep permission scoping. 11.6 Accessibility - labelled checkboxes, keyboard, accessible tree/calendar.
