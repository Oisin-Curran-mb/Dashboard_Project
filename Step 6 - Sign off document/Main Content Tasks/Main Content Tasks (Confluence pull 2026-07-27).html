Part A. What exists today

1. What it is

A quick-action launcher: a small grid of labelled icon tiles, each a shortcut straight to a common action or page, so users avoid hunting through menus. It is purely navigational - tap a tile, go to that part of the app.

SME This is the functional "My Tasks" the SME values and would use every day to avoid navigating complex menus - but he flagged that today it just says "enter transactions" without identifying which module it is, and that widgets like this land better when they are functionally oriented rather than report-oriented.

2. Where the data comes from

The tiles are not user-configured - the system chooses them automatically from the current page and the user's permissions; tasks the user cannot access are hidden entirely (not greyed). Up to 8 tiles appear. Source table: SSScreenSectionTask (tasks per page/section, with icons and navigation targets). Prior doc, to confirm.

Part B. Users and market

5. Personas

Serves everyone who does daily work, filtered to what each person may do. The bookkeeper/administrator (P1) is the primary user - quick access to the handful of actions they repeat daily (enter transactions, write a check, run payroll, create a PO). Because it is permission-aware, each role sees only its own actions.

7. Context scenarios

A. Daily work - bookkeeper taps a tile to enter today's transactions instead of walking the menus. B. Ambiguity - two "Enter Transactions" tiles, no module shown, so the user isn't sure which one to tap. C. Power user - wants to pin their six daily actions in a fixed order; can't. D. Restricted user - actions they can't perform are correctly hidden.

8. Competitor and analog benchmark

Desktop research The pattern is the quick-action / shortcut-tile launcher (QuickBooks "+ New" and shortcuts, Xero quick links, OnPay's customisable dashboard tiles, Bitdefender Quick Actions, OS quick-settings tiles). Consistent best practice: make tiles user-customisable (pin, hide, reorder, prioritise - OnPay exposes a visible/hide toggle per tile); label them specifically for the action, not generically; keep them permission-aware; cap and group so the set stays scannable; and give every tile a real accessible name (don't rely on the icon). Android's own tile guidance: reserve tiles for frequent, fast-access actions. Sources: OnPay, Android QS tiles, Bitdefender Quick Actions.

Part C. Designer brief

9. Target composition (what the widget should be built from)

The concrete make-up, so it can be built and demoed consistently. A floor, not a straitjacket. Triage: P current production (keep what works, delete nothing used), C competitor, SME Ben Lane, DR desktop/best practice, O Oisin's demo.

Controls (header):

  • Customise - let the user pin, hide, reorder and add tiles (standard + their own saved tasks), with a visible/hide model like OnPay's. [SME control; DR OnPay] The current auto-set becomes the default, not the only option.

Content:

  • A grid of specifically-labelled action tiles: icon + a label that names the module and action ("Enter AP Transaction", not "Enter Transactions"). [SME module ID; DR specific labels; P generic "Enter Transaction" tile verified live 23 Jul 2026]

  • A role-based default set of frequent, functional actions (enter transactions per module, write check, run payroll, new PO), permission-filtered. [SME consolidated standard+saved; DR defaults]

  • A sensible cap with overflow ("more") and optional grouping, rather than a hard 8 that silently truncates. [DR scannable; P up-to-8 verified live 23 Jul 2026]

Interaction & rules:

  • On the dashboard, present a stable, personalised set - don't silently swap tiles by page context when the widget lives on the dashboard. [P context-dependent today]

  • Tap navigates to the action (keep); consider returning to the dashboard afterwards. [P; My Status open question]

  • Every tile has a clear accessible name; keyboard operable; don't rely on the icon alone. [DR Android tile guidance]

  • Keep it permission-aware (hide disallowed actions). [P strength]

Relationship to My Status: Main Content Tasks = do an action (launcher); My Status = see what needs attention (counts). They are complementary; decide deliberately whether they stay as two widgets or converge into one "My Work" area. [product decision]

11. Significant design decisions

11.1 Make it customisable. The single biggest change the SME wants - let users pin/hide/reorder/add tasks; keep today's auto-set as the default. 11.2 Identify the module in every label - resolves the SME's core complaint; "Enter AP Transaction", not "Enter Transactions". 11.3 Stable set on the dashboard - don't shuffle tiles by page context when the widget is on the dashboard; a launcher users rely on daily should be predictable. 11.4 Functional, not report-oriented - bias the default set to daily actions (SME). 11.5 Cap + overflow + grouping instead of a hard 8. 11.6 Decide the My Status relationship - keep the counts router (My Status) and the action launcher (this) distinct, or converge into one "My Work" area; a deliberate product call, not an accident of two legacy widgets.
