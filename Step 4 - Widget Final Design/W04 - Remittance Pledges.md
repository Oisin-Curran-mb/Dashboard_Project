## Purpose

> **[v2 — 2026-07-28]** The built Final is Jo Lopez's remittance widget carried into the Final Check tab (the additive `remF` block) with owner deltas layered on top. Its default is a strictly-tabular Table view (Version A's report columns in Jo's style, no in-cell mini bar), with a Pacing Bars view available on a toggle (Option B's flat fill + navy expected tick, day-based colours). The purpose statement below is unchanged and still holds. [BUILD]

Shows how well the organisation is keeping up with its remittance pledge commitments. For each activity type, users can see what was pledged, how much has been paid, what remains outstanding, and the percentage paid so far.

Every data shape named above (pledged, paid, outstanding, percentage paid, per activity type) matches the legacy widget's documented column set [DOC — Step 1 research].

## How Other Companies Fulfil This Purpose
- **"Pledge vs. Received"** is a named, standard nonprofit fundraising metric, with an established fulfillment-rate formula (Received ÷ Pledged × 100; healthy range 85–95%) ([DonorSearch](https://www.donorsearch.net/resources/nonprofit-fundraising-metrics/)) — this is exactly the metric this widget already tracks as "% Paid," and is the direct justification for making **overall % Paid the KPI headline**. [RESEARCH]
- The standard visuals for this metric are progress bars, paired bars, or a pie/table — all three of which this widget's original options already were. [RESEARCH]

**Note:** no dedicated competitor product for denominational apportionment/remittance tracking specifically exists in the market researched — this is a niche church-finance concept, so the benchmark used here is the general nonprofit pledge-tracking pattern rather than a named direct competitor. This widget is already about as well-aligned with that general pattern as it can be.

## Data Contract
What the widget consumes, stated here rather than only linked out. All source tables and formulas below come from the Step 1 research doc, which was confirmed correct against the legacy `RMPledges : DataPanelControl` class (`/Remittance`), verified via `Widget_Comparison_Classic.html`, 2026-07-08 [DOC — Step 1 research].

> **[v2.1 — 2026-08-08] Pledge grain added to the contract.** The widget is pledge-driven, not activity-driven: each activity is a display bucket whose Paid and Outstanding are aggregates over the pledges beneath it, and an activity can carry hundreds of pledges (the Step 5 findings cite 500 to 800), so the drill must paginate or top-N and never dump them all. Each PLEDGE carries its OWN term and goal and belongs to a church or donor: goal = `RM_PledgeDetail.Pledge` (summed to the activity's Pledge/Annual total), term = `RM_Pledge.BeginDate` / `RM_Pledge.EndDate` (each pledge its own dates), church/donor name via `RM_Pledge.ChurchID`. Per-pledge expected-by-now is derived from that pledge's OWN dates (`goal * clamp(asOf - BeginDate, 0, termDays) / termDays`), never a shared calendar-year or month fraction. Activity Paid = sum of its pledges' Paid; activity Outstanding = sum of its pledges' Outstanding. "YTD Paid" is the activity's calendar-YTD paid-to-date (Jan 1 to the selected receipts-through date), i.e. `SUM(RM_HistoryDetail.Amount)` for posted, non-void receipts with `CheckDate <= asOf`. The per-pledge status ("behind" / "on track" and so on) is a design-only pacing signal with no backing column (the widget endpoint returns per-activity aggregate rows only, `RMWidgetActivityRecord`); it is computed from shortfall/days-behind at render time. Sources: `Step 5 - API documents/Remittance Pledges/` API Spec + the two 2026-08-08 findings docs. [DOC — Step 5]

## Interaction Spec

> **[v2.1 — 2026-08-08] Drill changed: activity click now expands an inline pledge table, not a popup.** The payment-history modal is REMOVED from the active behaviour but kept fully rollback-able behind a build flag `REMF_USE_POPUP` (default false); the modal code is untouched, so flipping the flag to true restores the old popup on activity click. With the popup off, clicking an activity row (in either the Table or the Pacing bars view) toggles open an INLINE pledge table for that activity (collapsed by default, expand/collapse per activity, a rotating caret as the affordance). That table lists the activity's pledges with columns Church/donor name, Begin date, End date, Goal (pledged), Paid, Outstanding, and a paired-text pacing status (never colour alone). Each pledge is paced on its OWN begin-to-end term. Default sort is most behind pace first (`shortfall = expectedByNow - paid`, descending), so later pages are progressively healthier. Pagination is real, 20 per page, with a numbered pager (the mock seeds about 60 to 72 pledges per activity so three or more pages are demonstrable). The receipts-through chip, the Table / Pacing bars toggle, the sort headers, the hover card and the accessibility layer all keep working as in v2. The v2 popup-drill description below is superseded by this block and recorded in Design History. [BUILD]

> **[v2.2 — 2026-08-08] Drill is Table-view ONLY; pledge name column is "Name".** Two owner changes on top of v2.1. (1) The inline pledge drill now lives on the **Table view only**. The other pledge columns (Begin, End, Goal, Paid, Outstanding, status) are unchanged. The v2.1 "either the Table or the Pacing bars view" wording above is superseded by this block. [BUILD]

> **[v2.3 — 2026-08-08] Pacing Bars rows clickable again: a popup with the top 5 pledges most behind.** The widget now has TWO distinct drills, one per view. (1) **Table view drill (unchanged):** clicking an activity row expands the inline, paginated (20 per page) pledge table in place, exactly as v2.1/v2.2. (2) **Pacing Bars view drill (new, restored):** the Pacing Bars view is no longer a dead overview. Its activity rows are clickable again (`role="button"`, `tabindex`, `aria-haspopup="dialog"`, Enter/Space activate, a subtle open affordance icon) and open a **popup/modal** built on the shell's existing modal pattern. The popup's **TOP** is the activity summary the old popup had, in this order: Total pledge, YTD Paid, Expected by now, Outstanding, % Paid, and the pacing-status chip, plus a pledge-term line. The popup's **LOWER SECTION** is that activity's **top 5 pledges most behind pace**: the activity's pledges sorted by `shortfall = expectedByNow - paid` (each pledge on its OWN term) descending, filtered to those actually behind (`shortfall > 0`), capped at 5, with NO pager. Each row shows Name (`CorePerson.DisplayNameLastFirst`, "Last, First"), Begin date, End date, Goal, Paid, Outstanding and a paired-text pacing status, using the same pledge-row markup as the Table drill. The section is headed "Most behind pledges" with a note: 5+ behind reads "Showing the 5 furthest behind of N pledges behind pace"; 1 to 4 behind reads "Showing all N pledge(s) behind pace" (and shows only those); none behind shows a clean "No pledges are behind pace" message. This popup shows **NO receipts / last-payment list**; that content is removed from it. The old receipts/payment-history popup (`remFDetailModalHTML`) is preserved and rollback-able, reachable only via `REMF_USE_POPUP` on the Table-view click (mode `history`); it is described in Design History. The Table drill, the Table / Pacing bars toggle, the receipts-through chip and the YTD Paid column are unchanged. [BUILD]

> **[v2.4 — 2026-08-08] The receipts filter is a DATE RANGE (behaviour a); the single "Receipts through" cutoff and its Refresh button are superseded.** The filter chip opens a popover with exactly **three** options and **no Refresh button**: **This year** (default), **Last 30 days**, and **Custom**. The chip label now reads **"Receipts from [start] to [end]"** with both dates formatted concisely (a shared year printed once, e.g. "Receipts from Jan 1 to Jul 31, 2026"), replacing the old "Receipts through [date]" text. The View toggle, sortable headers, both drills, hover card and the YTD Paid column are unchanged.
