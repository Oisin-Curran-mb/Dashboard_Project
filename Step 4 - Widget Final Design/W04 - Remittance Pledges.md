## Why v3 exists (2026-08-24) — read this before the sections below

The "Last verified against build" line above is a full changelog and hard to read at speed. This is the short version.

**The problem.** W04 and W17 Gifts & Pledges read near-identical data and had drifted into looking like the same widget. Nobody could say what distinguished them, and two SME interviews had failed to settle it (Ben Lane 13.07.2026 described both the same way; Edward Eoff 10.08.2026 explained W04's data model in depth but was never asked the comparison).

**The decision, per direct instruction 2026-08-24.** Split them by **role**, not by data:

| | **W04 Remittance Pledges** | **W17 Gifts & Pledges** |
|---|---|---|
| Question it answers | Which pledges are **not arriving as expected**, and by how much | How are we tracking **against goal** |
| Glance headline | Behind-pace shortfall in money | Percent of goal |
| Leading content | The exceptions, worst shortfall first | Goal progress per campaign |

**What that produced in the build:** a behind-pace money headline instead of a percentage (percentages of goals are W17's language, so the "% of pledged" pill was removed from Glance and the header); the table grouped into Behind pace / On track / No pledge in this range with the exceptions always open and the rest collapsed; a per-pledge payment schedule that names the **skipped payment**; and a date range whose start finally does real work.

**What it changes for the backend.** Recorded in full in [`Step 5 - API documents/Remittance Pledges/Remittance Pledges - API Spec.md`](../Step%205%20-%20API%20documents/Remittance%20Pledges/Remittance%20Pledges%20-%20API%20Spec.md), reopened to 🟡 Draft on 2026-08-24 because of these changes. Summary:

- `receiptsThrough` becomes a **`rangeStart`/`rangeEnd` pair**. `rangeEnd` is the only pacing anchor; `rangeStart` lower-bounds receipts and decides pledge scope. Old param kept as a deprecated alias.
- Two new response fields: **`windowPaid`** (receipts inside the window) and **`hasPledgeInRange`**.
- A new **pledge-in-scope overlap rule** (`BeginDate <= rangeEnd AND EndDate >= rangeStart`), which partly resolves the long-standing ended-but-unpaid drop-off question.
- A new **API 3, Pledge Payment Schedule**, for the skipped-payment drill.
- One explicit warning to the backend: **do not window-bound `paid`.** The frontend made that mistake mid-build and it made every pledge read as catastrophically behind, because it compares a windowed numerator against a cumulative denominator. Pacing is inherently cumulative.
- One rule for any future server-side total: shortfall must be **summed per row**, never netted, or a pledge running ahead masks one running behind.
- The previously academic "linear vs stepped `expected`" open item is **now load-bearing** — a skipped payment only exists if there are discrete scheduled payments to skip.
- **Blocking:** receipts-only rows need a query path that does not exist today. Edward tested it live and the widget shows nothing without a pledge. Awaiting an accept-as-risk-or-drop decision (Sign-off Readiness row 7).
- Terminology, from Edward: this control must **never** be labelled "fiscal" anything.

## Purpose

> **[v2 — 2026-07-28]** The built Final is Jo Lopez's remittance widget carried into the Final Check tab (the additive `remF` block) with owner deltas layered on top. Its default is a strictly-tabular Table view (Version A's report columns in Jo's style, no in-cell mini bar), with a Pacing Bars view available on a toggle (Option B's flat fill + navy expected tick, day-based colours). The purpose statement below is unchanged and still holds. [BUILD]

Shows how well the organisation is keeping up with its remittance pledge commitments. For each activity type, users can see what was pledged, how much has been paid, what remains outstanding, and the percentage paid so far.

Every data shape named above (pledged, paid, outstanding, percentage paid, per activity type) matches the legacy widget's documented column set [DOC — Step 1 research].

## How Other Companies Fulfil This Purpose
- **"Pledge vs. Received"** is a named, standard nonprofit fundraising metric, with an established fulfillment-rate formula (Received ÷ Pledged × 100; healthy range 85–95%) ([DonorSearch](https://www.donorsearch.net/resources/nonprofit-fundraising-metrics/)) — this is exactly the metric this widget already tracks as "% Paid," and is the direct justification for making **overall % Paid the KPI headline**. [RESEARCH]
- The standard visuals for this metric are progress bars, paired bars, or a pie/table — all three of which this widget's original options already were. [RESEARCH]

**Note:** no dedicated competitor product for denominational apportionment/remittance tracking specifically exists in the market researched — this is a niche church-finance concept, so the benchmark used here is the general nonprofit pledge-tracking pattern rather than a named direct competitor. This widget is already about as well-aligned with that general pattern as it can be.

## Data Contract
What the widget consumes, stated here rather than only linked out. All source tables and formulas below come from the Step 1 research doc, which was confirmed correct against the legacy `RMPledges : DataPanelControl` class (`/Remittance`), verified via `Widget_Comparison_Classic.html`, 2026-07-08 [DOC — Step 1 research].

> **[v2.1 — 2026-08-08] Pledge grain added to the contract.** The widget is pledge-driven, not activity-driven: each activity is a display bucket whose Paid and Outstanding are aggregates over the pledges beneath it, and an activity can carry hundreds of pledges (the Step 5 findings cite 500 to 800), so the drill must paginate or top-N and never dump them all. Each PLEDGE carries its OWN term and goal and belongs to a church or donor: goal = `RM_PledgeDetail.Pledge` (summed to the activity's Pledge/Annual total), term = `RM_Pledge.BeginDate` / `RM_Pledge.EndDate` (each pledge its own dates), church/donor name via `RM_Pledge.ChurchID`. Per-pledge expected-by-now is derived from that pledge's OWN dates (`goal * clamp(asOf - BeginDate, 0, termDays) / termDays`), never a shared calendar-year or month fraction. Activity Paid = sum of its pledges' Paid; activity Outstanding = sum of its pledges' Outstanding. "YTD Paid" is the activity's calendar-YTD paid-to-date (Jan 1 to the selected receipts-through date), i.e. `SUM(RM_HistoryDetail.Amount)` for posted, non-void receipts with `CheckDate <= asOf`. The per-pledge status ("behind" / "on track" and so on) is a design-only pacing signal with no backing column (the widget endpoint returns per-activity aggregate rows only, `RMWidgetActivityRecord`); it is computed from shortfall/days-behind at render time. Sources: `Step 5 - API documents/Remittance Pledges/` API Spec + the two 2026-08-08 findings docs. [DOC — Step 5]

## Interaction Spec

> **[v3.5 — 2026-08-30, per direct instruction] CURRENT: three pace cards filter a flat table; the v3.0 group headers are retired.** Ported from **Jo's `remFPaceCards`**: three cards above the table, **Behind / On track / Ahead**, each showing that band's activity count and outstanding money. Clicking a card filters the table to that band; clicking the active card clears the filter, because its own `data-v` carries `"all"`, as in her build. The table below is **flat** — the collapsible Behind pace / On track / No pledge in this range group headers from v3.0 are gone (`remFGroups` and `remFGrpHead` remain defined but unreachable, the gpFDonut rollback pattern). **Receipts-only activities are not a card and are never filtered away**; they render as a footer line under the table stating their count and money, because an activity with no pledge term in the window has no pace to band. **Band definition departs from Jo deliberately:** Behind is this widget's own `shortfall > 0` exception rule so it matches the header headline's "N of M behind pace" count, not her 30-day day-band, which would have contradicted it on the same screen; the remainder splits her way into Ahead (ahead or fully paid) and On track (on pace). The **Total row is unchanged** and still cross-foots every activity in scope including any hidden by a filter, stated explicitly in the caption whenever a filter is active. An empty band renders an explanation and tells the user to tap the card again. Cards appear at **Explore and Detail only**, not Glance, and **only on the Table view**: the Pacing Bars view renders no cards, so the pace filter does not apply there. Band colour sits on the card icon only; every card states its figures as text, so colour is never the only signal. [BUILD]
