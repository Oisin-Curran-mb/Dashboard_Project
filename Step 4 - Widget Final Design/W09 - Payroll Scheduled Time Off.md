# Final Design (current)

*This part describes only the shipped design (Final built 2026-08-07). Anything the build superseded (the earlier Department -> Employee -> Day structure, the old size table, the Calendar Year filter) has been moved to the dated Design History section at the very end of this doc, not deleted.*

## Purpose
Gives supervisors a view of all scheduled time-off requests, grouped by department (or pay group) and shown per person as one line per calendar day, with the ability to approve requests directly from the widget, plus a calendar view of who is out when for planning.

## How Other Companies Fulfil This Purpose
- Leave-management dashboards should surface leave balances, pending requests, and a **calendar view** for planning ([Synergy Codes](https://sub.synergycodes.com/our-work/leave-management-dashboard-for-hr-department-purposes/)).
- **One-click approve/reject**, including bulk actions, is called out as the core manager interaction for this exact workflow ([Factorial](https://help.factorialhr.com/en_US/absences-approvals/how-to-create-time-off-approval-systems)).

**Net assessment:** the two views below map directly onto the two standard leave-management treatments. This also confirms a decision already made earlier in this project: an earlier draft had dropped the approval workflow in favour of read-only views, which the standard shows would have been a real regression, not just a deviation from the old design.

## Data Table Sort
Intended: fixed — Department alphabetical, then Employee alphabetical, then Day chronological. Not user-changeable — predictable order matters more than flexible sorting for an approval workflow.

> **[BUILD MISMATCH — found 2026-08-30 by the unattended audit, not yet resolved]** The build only partly implements this. Reading `payFQueueOrdered`: the GROUP order is sorted alphabetically **only when Group by is Department** (`if (w.queueGroup==='dept') gOrder.sort();`) — with Group by set to Pay Group the groups come out in source-data encounter order. **Person order is never sorted**; people appear in the order their first matching row is encountered (in the mock, "Thomas Ade" precedes "Grace Lin" under Ministry). **Day-lines are never sorted chronologically** either; they follow the source entry order expanded per day, so one person can read Aug 12, Aug 13, Aug 14, Aug 3. This is a build gap against a documented rule, not a doc that fell behind, so it has deliberately not been "fixed" by rewriting the rule to match the code. Decision needed: implement the documented sort (a person sort plus a day sort in `payFQueueOrdered`, and an alphabetical group sort for the Pay Group dimension too), or restate the rule. Owner: project owner.

Trimmed-view rule: this widget has no "top N" trimmed size. There is no Small size (see Refresh note), and Medium collapses departments rather than truncating the list (see Size behaviour), so no top-N ranking rule is needed.

## Views (Switch View)

Two views, serving genuinely different purposes on the same underlying data, not just different chart types on the same story.

### View 1 — Approval Queue *(default)*
A clean row/column list with a Group by toggle: DEPARTMENT (default) or PAY GROUP as subheadings (Department first + default as of v2.7). Under each subheading, each PERSON is shown by name directly (the person is visible, not hidden inside a lower level), with the other dimension shown as a quiet secondary label. **The person row is an expander, collapsed by default (v3.0, owner-directed 2026-08-24).** Collapsed, it shows a caret, the name, the other dimension as a quiet secondary label, and either an "N pending" count badge or an "All resolved" chip. Opened, it reveals a Date / Type / Hrs / Status column header and that person's time-off **day-lines** (per-day model, v2.7: a multi-day request is one line per calendar day, individually shown, counted and approvable): the day's date, leave type (a plain text label, no icon), hours, and status ("Pending" or "Approved by [name], [date]", each a chip pairing colour with an icon and text). Actions: each person row carries a real labelled **Info button** beside the action column (v2.9) opening a coverage popover (that person's time off this year totalled by leave type as text, plus a same-dates coverage-overlap list of who else is off during this person's dates, each with department + pay group); each pending day offers an Approve button; an Undo on any Approved day returns it to Pending. **There is no person-level bulk approve**: "Approve all (N)" was removed in v3.0 (owner-directed 2026-08-24) precisely because, with the days hidden behind the expander, it would let an approver clear a whole month unseen. Approval is per day, inside an opened person. An outstanding (past-due pending) day-line carries a red "Outstanding" tag and a red row accent (v2.8); it still appears under the Pending filter and is still counted in the queue counts this pass (no separate Outstanding chip was added, pending an owner decision, see Sign-off Readiness). An inline three-chip Status filter offers All / Pending (default) / Approved. The view toggle, Group by toggle and Status filter use Jo's segmented toggle styling. This is the widget's core interaction and its reason for existing, so it leads. (Owner-directed 2026-08-07: this grouping -> Person -> day-lines hierarchy supersedes the earlier Department -> Employee -> Day expand/collapse structure, preserved in Design History. Per-day lines, Rejected removal, the three-chip filter and Department-first default are owner-directed 2026-08-08, v2.7.)

### View 2 — Leave Calendar
A genuine month calendar grid showing who is out when. Sunday-to-Saturday weekday column headers (**tiered as of v3.1, 2026-08-30: single-letter initials at Explore, three-letter abbreviations at Detail**, because seven three-letter labels crowd a 440px panel), a full weeks x days cell grid computed from the displayed month, adjacent-month days greyed, and today marked. **Calendar chrome, redesigned v3.1 (2026-08-30, owner, after reviewing a standalone before/after preview at both tiers):** cells sit on a uniform row floor (44px at Explore, 62px at Detail) so an empty week is no longer a thin strip and a busy week no longer stretches; the day number moved up to 11px, this file's norm, right-aligned to top-left; **status now uses one visual channel, not three** (the old cream `.has` cell fill is dropped and Approved / Pending are carried by an inset accent bar alone, which frees the cell background for real hover and selected states, the selected state tracking whichever day's popover is open — the calendar previously gave no indication which day the panel belonged to); Outstanding is the single exception that also gets a wash, deliberately weak (0.04, hover 0.09) so the only loud thing on the month is the state needing action; **today no longer resizes its cell** (it was a 1.5px border against 0.5px siblings, physically changing the current day's size) and instead gets a brand pill on the day number with a uniform 1px border throughout; markers align to the bottom of a floored cell; and the "+N" overflow is a real chip rather than stray text the cell's `overflow:hidden` could clip. Prev / next month navigation (chevrons with a month + year label) moves between months and re-renders; a month with no entries renders a clean empty-month state, not a blank or a throw. Each calendar day of a request is marked (per-day model, v2.7). A marker is now the person's **initials** coloured by that person's approval STATE (Approved green, Pending yellow/amber, and **Outstanding red** as of v2.8 for a still-pending day dated before today); there is no leave-type icon and no separate status glyph. The day CELL takes a priority colour when a day mixes states (any Outstanding red, else any Pending yellow, else all-approved green; no-request days stay neutral), so a mixed day shows differently-coloured initials inside the priority-coloured cell (a past day with a pending person reads red; a future pending day reads yellow; an approved-only day reads green). Initials are derived from the name as first-plus-last initial (Dana Whitfield reads "DW"), with a single-name fallback to the first two letters, shown at both Explore and Detail; the full name, leave type, dates, status and group stay in the marker `title` and the sr-only text label, and the day cell names its overall status in its aria-label, so colour is never the only signal. A day with more people than fit shows a "+N" overflow. **Clicking a day (or a specific marker) opens a day-detail popover** listing everyone out that day with name, both Department and Pay Group, leave type (text label, no icon), hours and status; it is informational (approvals stay in the queue), keyboard reachable, and dismissible via close control / click-away / Escape. The legend is a simple status colour key ("Colour = status": green Approved, yellow Pending, red Outstanding as of v2.8, each swatch paired with its status glyph and word); the leave-type icon key is removed (there are no leave icons). **The Group by toggle is gone from this view (v3.3, 2026-08-30, owner).** It read as the same control as the queue's while doing an unrelated job: markers have coloured by STATUS since v2.5, so switching it changed only the wording of a marker tooltip and one noun in the summary line. The calendar's grouping dimension is now fixed to Department, which is what the summary line, the day-detail grouping and each marker's group label use. **This view's own control is instead a Department filter (v3.2, 2026-08-30, owner: "so a manager can see only their own team")**: a native `<select>` offering All departments (default) or one department, derived from the data with a per-department count of PEOPLE out in the displayed month, reaching the grid, the summary line, the legend, the empty state and the day-detail popover. Changing it closes any open popover, which would otherwise still be showing people the filter has just excluded. A filtered month with no matches gets its own empty state naming the department and pointing back to All, distinct from "no time off scheduled this month", because a filter matching nothing is not the same as an empty month. The filter is calendar-scoped by construction: it runs through a calendar-only entry helper rather than the shared month-entries function, so the Approval Queue's rows and the Glance figures are provably unaffected. There is no breakdown list below the grid: the grid itself is the view. The planning/roster view, for when the question is "who is out when," not "what needs my approval."

## Accessibility

Required (project baseline):
- Colour is never the only signal: on the Leave Calendar colour encodes approval STATE (Approved green, Pending yellow/amber, Outstanding red as of v2.8), applied per marker and, by priority (any Outstanding red, else any Pending yellow, else all-approved green; no-request days neutral), to the day cell. Every state colour is paired with a non-colour signal: the state word (Outstanding / Pending / Approved) in each marker's `title` and sr-only label, the overall day state word in the day cell's aria-label ("some outstanding" / "some pending" / "all approved"), and the state words in the legend key. The marker itself is the person's initials (which also identify who). The leave type is carried as a plain text label (in the queue rows, day detail and Info panel), not an icon. In the Approval Queue each status chip carries an icon + colour + text label, and an outstanding row's red "Outstanding" tag carries an error icon and the word "Outstanding". *Verified in the build 2026-08-08 v2.8 (driver asserts the priority rule at both the unit and rendered levels, per-marker state colour, state words present as DOM text, red never appearing without the word "Outstanding", the status colour legend including red, markers carrying zero leave-type icons, and that flipping Group by leaves the day colours unchanged).* The Group by control was subsequently removed from the Leave Calendar altogether (v3.3, 2026-08-30), so that last assertion no longer has a control to exercise on this view; the queue's Group by is unaffected. The calendar's Department `<select>` (v3.2) is a native form control, so it carries keyboard and screen-reader support without extra work, and it has an `aria-label` naming what it filters.
- Day-detail popover is keyboard reachable and dismissible: calendar day cells and markers are `role=button` and tabbable (Enter / Space open the day detail), the popover is `role="dialog" aria-modal`, and it closes via a close control, click-away, or Escape. *Verified in the build 2026-08-08 (driver fires the real delegated click + Escape handlers and asserts open/focus/close).*
- Chart values exist as text in the DOM (sr-only or visible), not hover-only: each calendar day marker carries a screen-reader text label (person, type, dates, status, group) in addition to its `title`, and both Explore and Detail show the person's visible initials as the marker (v2.7). *Verified in the build 2026-08-08. The remaining gap is real `th`/scope table semantics and full keyboard focus order, below.*
- Table semantics are real (`th`/scope), and interactive controls (the approve/reject checkboxes, expand/collapse, view switch) are reachable by keyboard. *Not yet reviewed against the build.*

## 2026-08-08 (v2.9) — superseded: the inline-styled Approval Queue and the icon-only Info affordance

Until v2.9 the Approval Queue was built from inline-styled spans: 53 `style=` attributes and 22 hardcoded hex colours in the `payF` region, with `<span role="button">` in place of real buttons, and the group count badge went silent at zero, leaving the reader unable to tell a clear group from a failed render. v2.9 (owner: "match Jo's approval-queue styling, keep our filters and the Leave Calendar, make Info a real button beside Approve") restyled it onto Jo's tokenised `pto-*` approval-queue language over this file's own `.wt-row` base, with her `pto-l1` group row (count badge now stating BOTH outcomes, "N pending" or "All approved"), `pto-l2` person row with `pto-emp-meta`, and `pto-l3` day row with real `pto-abtn-appr` / `pto-undo` buttons and classed columns. Info became a real labelled `<button>` in the same action column as Approve. This was a restyle, not a rebuild: every handler name, the Group by control, the status filter chips, the Leave Calendar and its day-detail popover, the Outstanding treatment and the per-day model were all unchanged, so behaviour was identical. The current Final Design body describes the shipped styling; this note records what it replaced.

## 2026-08-24 (v3.0) — superseded: the flat always-expanded queue and the person-level "Approve all (N)"

From the 2026-08-07 Final until v3.0 the Approval Queue emitted **every day-line for every person, always**, and each person row carried a bulk **"Approve all (N)"** (N counting pending day-lines) that approved all of that person's pending days at once, with "All resolved" shown when nothing was pending. The Explore cap counted DAY-LINES (6), so it could cut a person's list in half and show 3 of their 5 days with no sign the rest existed. v3.0 (owner, three changes) supersedes all of that:

- **The person row became an expander, collapsed by default**, with a rotating caret, `aria-expanded`, and Jo's `pto-colhead` column header appearing inside an open person. The Explore cap now counts **PEOPLE** (6), so a person is shown whole or not at all.
- **The person-level "Approve all (N)" and its `approve-person` handler were REMOVED by owner decision.** With the days collapsed, a bulk button on a closed row would let an approver clear someone's whole month without ever seeing the days, which is the opposite of the intent. `approve-entry` on each day line is now the only route to approval; the collapsed row shows name, group and a pending count (or an "All resolved" chip) so you can still judge whether opening is worth it.
- **Scale was measured, not eyeballed:** v2.9 had ported Jo's 12px / `6px 11px` / radius-8px buttons verbatim, which reads correctly in her roomier layout and bulky in this dense queue. Buttons became 11px / `4px 9px` / radius 6px with 14px icons, the name 12px, meta and badges 10.5px, day rows 10.5px, and `.wt-row` padding tightened from `7px 14px` to `4px 12px`. Her colours, structure and class names were unchanged.

Untouched by v3.0: Group by, the status filter chips, the Leave Calendar and its day-detail popover, the Outstanding treatment, Info as a real button, and Undo. The current Final Design body describes the shipped v3.0 behaviour; this note records what it replaced.

## 2026-08-30 (v3.1) — superseded: the barely tier-aware Leave Calendar

Until v3.1 exactly ONE line of the calendar differed between Explore and Detail (max markers 2 vs 3), so the same drawing was stretched from a 440px panel to an 880px card. Cell height was whatever content forced, so a week with markers was tall and an empty week a thin strip; the day number was 9px, the smallest text in the widget despite being the primary wayfinding element; status was carried on THREE channels at once (a cream `.has` cell tint AND a 3px accent bar AND coloured markers), leaving no channel free for hover or selected on an element whose entire purpose is being clicked, so the calendar gave no indication which day an open popover belonged to; and `today` was `border:1.5px` against siblings at `border:.5px`, physically changing the current day's size. v3.1 (owner, after reviewing a standalone before/after preview at both tiers) fixed all of that: a uniform row floor (44px Explore, 62px Detail, deliberately not square), an 11px day number, ONE status channel (the cream fill dropped, Approved and Pending on the accent bar alone), a deliberately weak Outstanding wash as the single exception, `today` as a brand pill on the day number with a uniform 1px border, real hover and selected states with selected tracking the open popover, tiered chrome (single-letter weekday initials at Explore, three-letter at Detail; markers bottom-aligned; the "+N" overflow becoming a real chip), and seven loose hexes reduced to three tokens. Not touched: the day popover itself, Group by, the status filter chips, the marker function and its per-person status colours, and every handler name.

## 2026-08-30 (v3.2) — added: a calendar-scoped Department filter

New in v3.2 (owner: "so a manager can see only their own team"), so this is an addition rather than a supersession, recorded here because it shaped a constraint worth keeping. The obvious place to filter was the shared month-entries function, but it has four callers and two of them are the Approval Queue and the Glance KPI, which are required to stay scoped to the working month with counts unaffected; filtering there would have leaked a calendar-only filter into the queue and silently changed the Glance figure. The filter therefore got its own calendar-scoped helper used by the calendar and the day popover ONLY. It is a native `<select>` rather than a filter chip because `.filter-chip` is declared under nine roots in the mock and `.payf-root` is not one of them, so a chip would have rendered completely unstyled; the select also fits six options into a 440px Explore panel and brings keyboard and screen-reader support for free. It is described in the current Filters section and View 2.

## 2026-08-30 (v3.3) — superseded: Group by on the Leave Calendar

From the 2026-08-08 refine until v3.3 the Leave Calendar carried its own **Group by (Department / Pay Group)** toggle, identical in appearance to the Approval Queue's. The owner reported that the filters were not fully correct when swapping between the two views, and was right for a sharper reason than cosmetics: the same control with the same label did two unrelated jobs. In the queue it genuinely regroups the rows; on the calendar it did almost nothing, because markers colour by STATUS (they always have, since v2.5, and v2.7 explicitly reduced Group by to grouping and labels only), so switching it altered only the wording of a marker tooltip and one noun in the summary line. v3.3 removed it from the calendar and left the queue's untouched. The calendar's grouping dimension is now fixed to Department.

Also removed as dead code with the control: the calendar branch of the group toggle, the calendar group-set handler, and `payFGroupColor` — which turned out to be pre-existing dead code, defined once and called nowhere, and which was the only function in the widget that ever treated the calendar grouping as a colour dimension. **A v3.2 note was withdrawn as false, not reworded:** it had read "Colour is by department, so every marker here is the same; switch Group by to Pay group to tell them apart", asserting a behaviour without checking the marker function. The situation it warned about never existed. Deleting `payFGroupColor` is what makes that correction verifiable rather than merely asserted. Note that this doc's own v2.5 Design History entry above still says the `payFGroupColor` / `payFGroupOrder` / `PAYF_PALETTE` helpers "remain in the code"; as of v3.3 `payFGroupColor` is gone, while `payFGroupOrder` and `PAYF_PALETTE` remain and still feed no colour.
